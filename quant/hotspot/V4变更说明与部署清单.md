## 一、V3 被你/验证器抓出的口径瑕疵 → V4 如何根治

### 1.1 V3 的「尾盘近似」是一只承认了的隐患

V3 选股在 **T 日 14:55** 跑，读的是「含当日 bar 的日K」，其 `closes[-1]` 是**进行中的当日 bar**——V3 docstring 自己标注为「尾盘近似，非已收盘」。这在口径上仍不干净：

- 14:55 取的量比、涨幅都用的是**残缺当日量**，必须靠 `240/已交易分钟` 折算补偿；
- 选股锚点与成交锚点分属两个时点（T 日尾盘 vs T+1 开盘），概念上绕。

**V4 的根治思路**：选股放到**盘前**（T 日 09:25 前），此时当日 bar **尚未生成**，取数天然拿到的就是 T-1 完整日K；再叠加 `fetch(..., drop_today=True)` 双保险——即便平台因时间口径提前生成了当日 bar，也会被 `_strip_today` 就地剔除。**全链路只用已收盘数据，口径瑕疵彻底消除（无未来函数）。**

> 验证实测（V4 dict 模式）：`选股数据全为 T-1 及以前（无 T 日 bar，无未来函数）` ✓；`个股特征收盘口径 = T-1 真实收盘（锚精确）` ✓。

### 1.2 量比补偿在 V4 退场

V3 因为取的是「尾盘残缺量」才必须做 `(240/elapsed_min)` 折算。V4 选股用 T-1 完整日K，量比本身就是**全日量比**，无需折算。新增常量 `VOL_RATIO_ADJUST = False`，相关折算分支被关掉——逻辑更简、且不再依赖「当前是第几分钟」这个盘中状态。

### 1.3 建仓窗口与护栏基准的口径拆分（V4 核心）

```
T 日 10:00  buy_job：
  · 快照价 p_now = 当日进行中 bar 的 close   ← 唯一的实时成交基准
  · 护栏基准 c_prev = rows[-2] 的 close = T-1 真实收盘  ← 已收盘、精确
  两个口径显式拆开（不再混用）：
      低开不接刀：p_now < c_prev × (1 - 1.5%)   → 放弃
      高开不追：  p_now > c_prev × (1 + 3.0%)   → 放弃
  限价 = min(p_now × 1.005%, c_prev × 1.03%)    ← 保证成交又不追高
```

与 V3 的关键差异：**V3 的护栏/限价基准是 T 日真实收盘（于 T+1 读取）**；**V4 的护栏基准是 T-1 真实收盘（盘前已确定）**。V4 因为选股在盘前完成，成交那一下只需要「T-1 收盘」作为护栏 +「10:00 快照」作为成交价，二者都已精确、无未来函数。

> 验证实测（V4 dict 模式）：`600013 快照(10:00)=16.55 护栏基准(T-1收盘)=16.47 限价=16.63` ✓，且 `限价 = min(快照价×1.005%, T-1收盘×1.03%)；护栏基准=T-1收盘` ✓。

## 二、V4 时间线（核心设计）

```
T 日 盘前   before_trading_start
              ① 冷静期衰减 / 持仓天数+1 / 持仓日K缓存（供盘中零取数风控）
              ② ★信号层★ 全池批量取数（drop_today=True）→ 板块强度
                 → 三阶段 → 主线(3条) → 候选(每板块只取前2只)
       ↓ 候选只存代码与特征，不存成交价
T 日 09:35  early_job
              ① 补卖昨日"可卖=0"的排队单
              ② 若盘前信号层失败（g.sector_state 为空）则重试一次
T 日 10:00  buy_job        ← 唯一建仓窗口（用户指定）
              ① 取当日进行中 bar close = 快照价 p_now（成交基准）
                 取 rows[-2] close     = T-1 收盘 c_prev（护栏基准）
              ② 双护栏：p_now < c_prev×(1-1.5%) 走弱不接刀；
                        p_now > c_prev×(1+3%)   涨过头不追
              ③ 每板块限 2 只（含已有持仓）→ order_value(..., limit_price=)
T 日 盘中    handle_data        每分钟风控（零额外取数：日K在日初已缓存）
T 日 14:58  risk_fallback_job  盘内兜底风控
```

**为什么 V4 选股在盘前天然更干净**：盘前无 T 日 bar，`fetch` 拿到的日K最后一根就是 T-1 完整收盘；`drop_today=True` 是防御性双保险。V3 那种「尾盘快照到底算不算已收盘」的纠结在 V4 里不复存在。

## 六、上线前必须自己核对的平台接口

代码已对下列每一点做了容错或降级，但**降级不等于正确**——降级会打日志，请确认日志里没有异常项：

| 接口 | 代码行为 | 要确认 |
|------|---------|-------|
| `get_history(..., is_dict=True)` | 探测 `dict / multiindex / single` 三形态 | 形态是哪一个；是否为 single（会收缩扫描范围） |
| `get_history(..., fq="pre")` | 不支持则告警后改不复权 | 是否出现 fq 降级告警（复权口径变了，信号会跟着变） |

## 七、已知未解决（不在本次范围，需你决策）

1. **板块池题材陈旧**——`sector_map.json` 的 `source` 实测是 **sina**（原方案写的是"akshare 拉东财/同花顺"，口径不一致）。175 个概念里含"机器人/低空/固态/算力/AI/芯片"的只有 2 个，近两年主线题材大面积缺失；行业侧还混进了「次新股」「其它行业」。→ 需要用东财/同花顺源重新生成静态池。
2. **静态池滞后 ≤7 日**——热点周期常仅 3-5 天，滞后一周等于结构性慢一拍。→ 建议改为日频刷新；若能做到，用当日实时涨停统计做动态板块聚合更好。
3. **三阶段依赖内存历史**——`g.prev_signal` 在策略重启后为空，重启首日退化为"启动期"。→ 若要跨重启保持，需落盘（只读目录外的可写区）。
4. **强度公式权重仍是拍定的**（50/10/20/1）——需要回测校准，本次未做。
5. **未做历史回测**——本版只完成"逻辑正确性离线验证"，对应原方案 M3（本地真实行情全链路回放）尚未执行。
6. **★V4 新增★ 10:00 建仓当日被 T+1 锁定**——V4 在 T 日 10:00 买入的仓位，当日不可卖（T+1 制度），风控的"可卖=0 入次日队列"逻辑会自然处理，但意味着：**信号（盘前定 T-1 热点）→ 建仓（T 日 10:00）这一拍本身就有 1 个交易日的时滞**，热点若只在 T 日当天发酵、T+1 即退潮，V4 会买在相对高位。这是"盘前定热点 + 早盘建仓"模式的固有约束，非代码缺陷；若想进一步贴近日内，可考虑把选股基准改为"盘前 T-1 + 10:00 实时涨停强度再过滤"两段式（本次未做）。

## 第九节 回测"0 成交"根因与 V4.1 补丁

**现象（2026-09-14 回测，区间 2026-08-26 ~ 09-11）**：连续 12 个交易日日志均为
`[信号] 批量取数 0/5645 只成功` → `全池取数为空（数据层故障）` → 每日 10:00「今日无候选，不建仓」。板块池正常载入（行业496 概念504），但 `get_history` 全程取不到数据。

**根因**：`_hist_call` 原逻辑仅在 `fq="pre"` **抛异常**时才降级不复权；而本券商（山西证券 PTrade）`get_history(..., fq="pre")` 返回的是**空结果（不抛异常）**。代码把"无异常"当成"fq 可用"，永久以 `fq="pre"` 取数 → 每批皆空。这违反 `ptrade-strategy-dev` 的 **R4（任何接口降级都要显式告警，绝不静默换口径）**。

> 为什么日志看不到异常？因为空 dict `{}` 仍满足 `isinstance(r, dict)`，模式探测判为 `dict`；逐批 `for k,v in {}.items()` 直接空转，既不抛异常也不触发"列名缺失"降级 → 全程静默 0 行。

**修复（V4.1，已落到 `hotspot_trader_v4_ptrade.py`）**：
1. 新增 `_has_data()`：对 `fq="pre"` 的返回做**空结果判定**（空 dict / 空 DataFrame 一律视为不支持），自动改不复权重试，并 `log.warning` 显式告警（满足 R4）。
2. `fetch` 首批次新增 `[诊断]` 日志：打印真实 `get_history` 返回形态（`type` / dict 键数 / 首值 `type`+`len`+`repr`）。**若补丁后仍 0 行，凭此日志即可区分是"复权口径"还是"返回形态不匹配"**——后者需再修 `_rows_from_any`（当时仅兼容 DataFrame / dict / list 三种，缺 numpy 结构化数组分支——见第十节）。

**验证**：四模式离线验证仍全绿（98+98+100+100 = 396 项，0 失败），补丁未改变既有逻辑。

**上线前必做**：重新跑一回测，确认日志出现 `[诊断] get_history 返回 type=...` 且 `[信号] 批量取数 X/5645 只成功` 中 X 显著大于 0。若 X 仍为 0，把 `[诊断]` 那几行日志发我，据此定是返回形态问题。

## 第十节 二次修复：解析层不识 numpy 结构化数组（V4.1.1）

**现象（2026-09-14 第二次回测，同区间 08-26~09-11）**：仍 `0/5645`，但 `[诊断]` 日志首次暴露真相：
```
[诊断] get_history 返回 type=OrderedDict mode=dict
[诊断] dict 共 200 键 示例keys=['301520.SZ','688046.SS','688202.SS']
[诊断] 首值 type=ndarray len=70 repr=array([(20260519,41.48,41.14,42.18,40.52,594200.), ...])
[盘前] 降级/异常 2 项:
   - [hist] 带 fq='pre' 取数为空（疑似不支持复权），改不复权重试
   - [signal] 全池取数为空（数据层故障），本日不生成信号
```
关键判读：`get_history` **确实返回了真实数据**（OrderedDict / 200 键 / 每值 numpy 结构化数组 70 行），却被丢弃 → `0/5645`。

**根因（第二层 bug，叠加在 V4.1 之上）**：V4.1 的 `_has_data` 只解决了"复权空结果"误判，但 `_rows_from_any` **完全没有 numpy.ndarray 分支**——该函数只处理 DataFrame / dict / list 三种载体。真实 PTrade 在 dict 模式下每个板块值是 numpy 结构化数组（`dtype.names=('date','open','close','high','low','volume')`），落到函数末尾 `return []` → 全部解析为空。于是 `_has_data` 又把"解析空"误判成"fq=pre 空结果"触发降级，两层 bug 叠加成 `0/5645`。

**修复（V4.1.1，已落到 `hotspot_trader_v4_ptrade.py`）**：在 `_rows_from_any` 补 numpy 结构化数组分支：
- 优先按 `dtype.names` **字段名**提取（`date/open/close/high/low/volume`），不依赖位置；
- 无字段名（普通 2D 数组）按位置 `(date,open,close,high,low,volume)` 退化解析；
- 价格转 float、0/NaN 行跳过，归一化为 `[date,close,high,low,vol,open]` 升序。

诊断数据验证：首行 `(20260519,41.48,41.14,42.18,40.52,594200)` → 解析为 `(20260519, close=41.14, high=42.18, low=40.52, vol=594200.0, open=41.48)`，`high≥close≥low` 且 `open` 介于高低之间，OHLC 自洽，确认字段映射正确。

**验证器同步加固**：`verify_v4_mock.py` 新增【21】测试，直接构造形如诊断的 numpy 结构化数组（及无字段名 2D 数组）喂给 `_rows_from_any`，断言解析行数 / 各字段映射 / OHLC 自洽。四模式合计 **444 项断言 0 失败**（原 396 + 新增 48 项真实形态覆盖）。

**现状澄清**：`fq="pre"` 本券商**实际是支持的**——之前"空"是解析 bug 的假象。修复后 fq=pre 数据被正确解析，`_has_data` 不再误降级，信号层能正常拿到 T-1 日K。请重跑回测，预期 `[信号] 批量取数 X/5645` 中 X 接近 5645，并出现真实主线/候选；届时 `10:00` 建仓层应能拿到候选。
